# إعداد Supabase لتطبيق Smart ATS

التطبيق لا يحتوي أي بيانات تجريبية. كل ما يعرضه يأتي من Supabase، وكل القراءات والحالات تأتي من بورد ESP32 (أو من مشروع المحاكي smart-ats-simulator أثناء التجربة).

## 1. قاعدة البيانات

ملفات الترحيل في `supabase/migrations/` مرقّمة بالتاريخ، وكل ملف يُشغَّل **مرة واحدة فقط وبالترتيب**:

| الملف | المحتوى |
|---|---|
| `20261116000000_smart_ats_schema.sql` | الأساس: الجداول، الصلاحيات (RLS)، دوال البورد والتطبيق |
| `20261118000000_reliability_and_security.sql` | الموثوقية والأمان: استقبال لا يتعطل بحقل خاطئ، `boot_id`، حماية ساعة البورد، الاحتفاظ بالبيانات، خصوصية الملفات الشخصية، المولد كمصدر عادي، أوقات الطاقة الشمسية |
| `20261119000000_invitations_by_email.sql` | الدعوات حسب البريد الموثّق: من يدخل بـ Google (أو لم يفتح رسالة الدعوة) يرى دعواته ويقبلها داخل التطبيق |

### مشروع موجود (شغّلت الملف الأول سابقاً)

افتح Supabase Dashboard ← مشروعك ← **SQL Editor** ← **New query**، والصق محتوى **الملفات التي لم تشغّلها بعد فقط**، كل ملف لوحده وبالترتيب، واضغط **Run**. بياناتك تبقى كما هي.

> لا تُعِد تشغيل ملف قديم بعد تشغيل ملف أحدث منه.

### مشروع جديد فارغ

الصق محتوى `supabase/dist/full_install.sql` (كل الملفات مجمّعة بالترتيب) واضغط **Run**.

### ما تنشئه الملفات

| الجدول | المحتوى |
|---|---|
| `profiles` | بيانات المستخدم. كل مستخدم يرى ملفه فقط؛ أعضاء الجهاز يُعرضون عبر `list_device_members` (الهاتف يظهر للمسؤول فقط) |
| `devices` / `device_secrets` | الأجهزة، وأسرارها (رمز الجهاز وPIN مشفّرين ولا تقرأهما الواجهة) |
| `device_members` | من يحق له الوصول لكل جهاز ودوره (مسؤول / مشاهد) |
| `device_status` | آخر حالة أرسلها البورد، مع `boot_id` و`clock_invalid` وعدد الأحداث المرفوضة |
| `telemetry` | القراءات الخام للرسم اللحظي (تُحذف بعد 3 أيام) |
| `energy_hourly` | تجميع ساعي لعدادات الطاقة لكل مصدر (لا يُحذف) |
| `events` | سجل الأحداث (يُحذف بعد سنة) |
| `device_settings` | إعدادات الجهاز مع رقم إصدار، ومنها أوقات استخدام الطاقة الشمسية في الوضع الذكي |
| `device_commands` | أوامر التحكم ودورة حياتها (المنتهية تُحذف بعد 30 يوماً) |
| `invitations` | الدعوات (رابط لمرة واحدة، صالح 72 ساعة) |
| `notifications` / `notification_preferences` | الإشعارات (تُحذف بعد 90 يوماً) وتفضيلات كل مستخدم للأنواع الخمسة |

## 2. المهام المجدولة (pg_cron)

- فعّل **Database ← Extensions ← pg_cron** قبل تشغيل الملفات (أو أعد تشغيل آخر ملف بعد تفعيله).
- مراقب الاتصال يعمل كل 10 ثوانٍ، ويحوّل الجهاز إلى «غير متصل» ويرسل إشعاراً إذا لم تصل بيانات لأكثر من 30 ثانية.
- تنظيف البيانات القديمة يعمل يومياً الساعة 03:15 UTC.

## 3. المصادقة (Authentication)

1. **URL Configuration**: ضع رابط التطبيق في **Site URL**، وأضف في **Redirect URLs** كل رابط تفتح منه التطبيق، مثل:
   - `http://localhost:5173/**` (التشغيل على حاسبتك)
   - رابط النشر (مثل Netlify)
2. **Confirm email**: أثناء التجربة يمكن إيقافه مؤقتاً من **Authentication ← Providers ← Email**. **أعد تفعيله** قبل أن يستخدم التطبيق أي شخص آخر، وإلا يستطيع أي أحد إنشاء حساب ببريد غيره.
3. **SMTP مخصص** (Authentication ← Emails ← SMTP Settings): خادم البريد المدمج يرسل فقط لأعضاء فريق المشروع وبعدد محدود. تأكيد الحساب وتغيير البريد والدعوات تحتاج SMTP. مع Gmail: فعّل التحقق بخطوتين، وأنشئ كلمة مرور تطبيق من `myaccount.google.com/apppasswords`، ثم: Host `smtp.gmail.com`، Port `465`، Username = عنوان Gmail، Password = كلمة مرور التطبيق.
   - **قوالب الرسائل بالعربي**: الصق ما في `supabase/email-templates.txt` في Authentication ← Emails ← Templates (Magic Link تُستخدم للدعوات، وConfirm signup، وReset Password).
4. **الدخول بـ Google**:
   - Google Cloud Console ← مشروع جديد ← **Google Auth Platform** ← Get started: اسم التطبيق، بريد الدعم، **External**.
   - **Clients ← Create client ← Web application**، وفي Authorized redirect URIs: `https://<project>.supabase.co/auth/v1/callback`.
   - انسخ Client ID وClient secret إلى Supabase ← Authentication ← Sign In / Providers ← **Google**.
   - ما دام التطبيق في وضع **Testing**، أضف كل من سيدخل بـ Google في **Audience ← Test users** (حتى 100 حساب). النشر الكامل يحتاج رابط سياسة خصوصية في صفحة Branding (مع مرحلة تطبيق الهاتف).
   - في تطبيق أندرويد لاحقاً يُضاف Client ثانٍ من نوع Android (اسم الحزمة وبصمة SHA-1)، ويبقى Client الويب كما هو.
5. **التحقق من الهاتف**: فعّل **Phone** provider واربطه بمزوّد SMS (مثل Twilio، مدفوع). حتى يتم ذلك يرفض التطبيق تغيير الرقم برسالة واضحة.

## 4. تسجيل الأجهزة

كل بورد يُسجَّل مرة واحدة من SQL Editor:

```sql
select public.register_device('ATS-000123');           -- جهاز تشغيل
select public.register_device('ATS-TEST01', 'test');    -- جهاز اختبار (يظهر فقط في نسخة VITE_APP_ENV=test)
```

الناتج يظهر مرة واحدة: `token` يُخزَّن في البرنامج الثابت للبورد، و`pin` يُطبع على ملصق الجهاز. المستخدم يضيف الجهاز من التطبيق بالمعرّف وPIN فيصبح مالكه.

## 5. بدون بورد حقيقي

محاكي البورد صار مشروع منفصل اسمه **smart-ats-simulator**، وبيه:

- **تطبيق هاتف** تتحكم من خلاله بالكهرباء والأعطال والسيناريوهات.
- **محاكي للحاسوب** يشتغل بـ `npm run emulator`.

الاثنين يحتاجون معرّف الجهاز والتوكن من الخطوة السابقة. التفاصيل بملف README الخاص بذاك المشروع.

## 6. الاختبارات

```bash
npm test          # كل الاختبارات: المنطق، الواجهة، قاعدة البيانات (PGlite)، وجلسة بورد مسجّلة مع قاعدة البيانات
npm run check     # الأنواع + الفحص + الاختبارات + البناء (نفس ما يشغّله CI)
```
